## 4. Findings

### F1 — blocking — non-UTF-8 path bytes are recorded lossily as Observed, and distinct paths collide

- **Evidence.**
  - [Observed] `code-structure.ts:91-97`: `defaultRunGit` decodes git's stdout with `encoding: 'utf8'` (`:93`). That is Node's replacing decoder: every invalid UTF-8 byte becomes U+FFFD.
  - Under `-z`, git emits path bytes raw, so a committed non-UTF-8 name reaches `parseGitLsTree` already corrupted, and it is accepted.
  - The docstring the diff adds (`code-structure.ts:104-105`) says "`-z` keeps every path byte-exact". The new test title (`code-structure.test.ts:97`) says "a non-ASCII byte exactly as committed". Both are false for this input class.
  - [Observed] Probe `district.json`: two top-level directories `\xe8te/` and `\xe9te/` give new paths `["�te/a.ts", "�te/a.ts"]` and one Orrery district `"�te"` with `fileCount: 2`. The old code gave two districts.
  - [Observed] Probe `probes.json`: `\xf1.md` and `\xf2.md` both become `�.md`, classified `markdown`.
  - [Observed] The sibling readers of the same parser already fail closed on this input:
    - `project-shape-model.ts:545`: `new TextDecoder('utf-8', { fatal: true })`;
    - `project-shape-observation.ts:376`: `decodeUtf8` → "produced non-UTF-8 output";
    - `git-object-reader.ts:279`.
- **Failure scenario.**
  - A repository with a legacy Latin-1 filename gets an Observed inventory whose path names no file at that commit. POC-REQ-001's oracle (`git rev-parse R:<path>`) fails on the served path, which is the falsifier.
  - Two such names collapse into one path string, and two such directories collapse into one Orrery district. The district count is a confident wrong Observed (VIS-2) that the old code did not produce. The old code's C-quoted form was wrong but injective under the default `core.quotePath`.
  - The change is the one that introduces the collision.
- **Proposed fix.**
  - Decode strictly, as the three PWB readers do. Have `defaultRunGit` return the bytes (or decode with `new TextDecoder('utf-8', { fatal: true })`). On a decode failure, return Unknown with a named reason that is distinct from "unreadable", for example "code-structure observation produced a non-UTF-8 path".
  - Minimal alternative: treat any `entry.path` containing U+FFFD as malformed. This also covers injected `runGit` strings. Its cost is that a genuinely committed U+FFFD name becomes Unknown, which is fail-closed.
  - Add a fixture test built with `git mktree -z` holding two non-UTF-8 names. Correct the docstring and the test title.
  - List this changed output in the PR. The old output was a quoted Observed. Fail-closed Unknown is the VIS-2 outcome, because a JS string cannot carry the bytes faithfully. If the lead reads the result as outside the owner-listed change "quoted paths are recorded", the bead's scope rule says to return it to the owner as a decision bead under `syzygy-bpyt.1`. Either way, do not ship the lossy Observed.

### F2 — note — a path beginning with `"` or containing LF makes the whole inventory Unknown (the disclosed residual)

- **Evidence.**
  - [Observed] `git-tree.ts:35` rejects any path that starts with `"` or contains `\n`. The check exists to catch C-quoted paths from a caller that forgot `-z`. Under `-z` such a record is well-formed, so here the check only refuses real paths.
  - [Observed] Probes: a single `"vendor/` directory, a single `"lead-quote.md` or a single `line\nbreak.md` turns the whole inventory Unknown. The differential's row "real repo: all eight awkward names" shows the same.
  - [Observed] The new assertion `code-structure.test.ts:132` feeds the record `…\t"\\303\\261.md"\0`. Under `-z` that is a real path beginning with a quote, so the assertion pins the residual as intended behaviour.
  - [Observed] The Unknown reason, "malformed inventory entry", misnames the cause: the entry is well-formed and the parser refused it.
- **Judgement.**
  - [Inferred] Acceptable for this bead. The outcome is fail-closed, with a named reason and no partial inventory, so it is lawful under VIS-2 and POC-REQ-003. It replaces an output that was already wrong (the C-quoted path recorded as Observed). Such paths are rare.
  - Fixing it means changing `git-tree.ts`, which `project-shape-model.ts:554` and `project-shape-observation.ts:526` share at the PWB trust boundary. Changing the default would alter what the PWB readers accept: an unlisted gate change that returns to the owner.
  - The output is still not the owner-listed one ("quoted paths are recorded, not dropped"), so it must not travel silently.
- **Failure scenario.** A repository that commits one file whose name begins with `"` loses its whole Orrery map to "Unknown (malformed inventory entry)".
- **Proposed fix.**
  - In this PR, list it explicitly among the changed outputs and in the class-3 owner notice.
  - File a follow-up bead under `syzygy-bpyt.6` for an opt-in strict mode, for example `parseGitLsTree(raw, { nulTerminated: true })`. It would drop the quote and newline heuristics and the newline fallback, and accept only NUL-terminated records. Code structure opts in; the PWB callers keep today's behaviour until they are reviewed separately.
  - Update `code-structure.test.ts:132` when that lands.
