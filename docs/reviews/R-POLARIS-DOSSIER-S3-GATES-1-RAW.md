## Findings

1. (blocking) [Observed] `reverifyPinnedRevision` never re-derives whether the subject is governed, so the per-project statement requirement can be bypassed at every later step. It re-checks the statement only when the stored record cites one (packages/polaris-dossier/src/reverify.ts:44-48). It never re-reads the project input and never re-lists the tree at the recorded pin. Two concrete routes, both reproduced against the merged code with the repository's own fixtures:
   - (a) Moved pin, with no other edit. Init at commit A (non-governed: drawer stated absent, no openspec/.syzygy path), so `providerStatement: null`. Rewrite `subject.pinnedRevision.commit` to commit C, which is consented and holds `openspec/specs/x/spec.md`. Result: `reverifyPinnedRevision` returns `ok: true` with no statement anywhere. The repository's own test codifies this as intended (packages/polaris-dossier/src/start-gates.test.ts:371-375). Later steps would then read, check and render a governed tree under a run that no in-force per-project statement covers. 033 says: "For a governed subject ... Syzygy SHALL refuse to issue a brief unless an in-force, recorded, per-project statement names the operator's agent provider". The governed predicate is defined over "the tree at the pinned revision", and the pinned revision is now C.
   - (b) Downgraded record. Init at commit B (governed, relying on STATEMENT-REDIS-ANTHROPIC@1). Edit run.json to set `governed.kind: "non-governed"` and `providerStatement: null`, which `readSubject` accepts (packages/polaris-dossier/src/run-record.ts:139-143), then withdraw the statement. Result: the guard returns `ok: true`. 033: "its withdrawal SHALL refuse further steps of any run that relies on it." The run.json is within the agent sessions' write reach by the spec's own threat model. 033 also says "Every value Syzygy shows that it cannot re-derive at that step SHALL be labelled Inferred", and the governed decision is re-derivable (project input plus a pinned-tree listing), so the guard must not rest on the stored kind.
   - Repair direction: in the guard, recompute `governedSubject(await sources.projectInput.drawerFor(repositoryId), <listing at recorded commit through the re-hashing reader>)`. Require a live statement whenever `statementRequired`, whatever the record says. Refuse if the recomputed kind differs from the recorded one, or if a statement is required and the record cites none or another. Replace the test at start-gates.test.ts:371 with a case asserting that a pin moved from a non-governed to a governed consented revision refuses. Add the downgraded-record case.

2. (revise) [Observed] Moving the pin between consented revisions is otherwise undetected by the guard, and S6, S8 and S9 cannot repair it as the PR plans. The PR body and start-gates.test.ts:371 delegate this to the later steps ("that the draft, inventory and verdict name the pinned revision is the later steps' check"). But the draft, inventory and verdict, like run.json, are all written by the agent sessions, so an agent that moves the pin can name the new revision consistently everywhere. Spec scenario "Recorded revision altered" catches only an unconsented target or a mismatch the agent chose to leave. [Inferred] Apart from finding 1, the consent harm is bounded, because the target is still a consented revision, and 033 makes "which consented revision the run was pinned to" Inferred. The safety argument therefore holds only once finding 1 is fixed. Separately, the guard does not compare the recorded `pinnedRevision.label` or `consentRecord` with what the consent now says for that commit. A probe that moved the pin to B kept `label: "fixture-a"` and passed (reverify.ts:39-50). Later renders must therefore show the label and consent record re-derived from the guard's `consentRecord` result and the live revision list, never from run.json. A follow-up bead should state this for S6, S8 and S9 explicitly.

7. (note) [Observed] The governed predicate is sound for the stated cases. It counts any segment equal to `openspec` or `.syzygy` after `toLowerCase`, at any depth (governed.ts:31-33). `listTree` emits every non-tree entry, including symlinks (120000) and gitlinks (160000), and refuses rather than truncates on budget (git-object-reader.ts:190-198, 294), so a symlink or submodule entry named `.syzygy` or `openspec` is counted. Residuals, all [Inferred]:
   - `toLowerCase` is not Unicode case folding. A segment such as `openſpec` (U+017F) or `.ſyzygy` is not counted, yet on a case-insensitive APFS volume it could satisfy a lookup of `openspec`.
   - NTFS-equivalent spellings (`openspec.`, `openspec `) are not counted.
   - A tree entry `openspec` that is an empty tree yields no listed path.
   - Submodule contents are outside the pinned tree, so they are not counted. That matches "the tree at the pinned revision" but should be disclosed.
   Consider NFKC plus case folding, and stripping trailing dots and spaces, before the segment compare. No fixture exercises a symlink or gitlink entry through `init`. gate-parts.test.ts:114-119 covers only path strings.
