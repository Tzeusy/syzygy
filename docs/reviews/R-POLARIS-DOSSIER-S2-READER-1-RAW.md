## Summary answer to question 1

No construction tried made the reader return bytes other than those the pinned identifier commits to without a refusal. [Observed] Every object returned passes `verified` (git-object-reader.ts:206-212), which hashes `"<type> <len>\0" + body` under the identifier's algorithm and compares it with the identifier the walk reached it by; commit, every tree on the path and the blob all go through it (lines 108, 149, 131). Substitutions tried and refused with `identifier-mismatch`: an `.idx` that maps the wanted id to another object's pack entry, and a ref-delta whose base is a different object (both PoC `swap`). A self-referential ref-delta refuses at the chain cap after 293 ms (PoC `cycle`). Offset deltas cannot cycle because the base offset must be strictly lower (line 255) [Observed]. Integrity therefore rests on second-preimage resistance of the hash (finding 9). The findings below are about refusal shape, hangs, resource cost, path hygiene and test/mutation coverage, not about substituted bytes.

Question 2: [Observed] the module imports only `node:crypto`, `node:fs/promises`, `node:path`, `node:zlib` (lines 1-4); filesystem calls are `lstat` (188, 196), `readdir` of `objects/pack` (192), `readFile` of `.idx` files and loose objects (194, 216, 273) and `open` of `.pack` files (296). No ref, config, hook, index, grafts, shallow, replace ref or alternates file is read; `objects/info/alternates` is only `lstat`ed to word the refusal (196, 222). Nothing spawns a process. The source-pattern test (test.ts:291-300) guards this. One gap: symlinks are followed, which gives a de facto alternate (finding 2).

## Findings

1. (revise) Several malformed stores escape as untyped exceptions, not as a `GitObjectReadRefusal` with a machine reason. 033 requires refusal "with its reason in human and machine form", and the PR text says a refusal "is a `GitObjectReadRefusal`". [Observed] PoC `bigoffset`: an `.idx` 64-bit large-offset entry of 2^60 makes `fh.read` throw `RangeError: The value of "position" is out of range` (offset from line 320, read at line 305). [Observed] PoC `idxdir`: a directory named `pack-y.idx` beside an all-loose store throws `EISDIR` from `readFile` at line 194, and no object is read. [Inferred] Also untyped: a large-offset index past the large-offset table (`readBigUInt64BE` at line 320 reads past the buffer's end once it runs beyond the 2×width trailer), and an `.idx` over 2 GiB (`ERR_FS_FILE_TOO_LARGE` at line 194). No content leaks, but a caller that maps `GitObjectReadRefusal` to the run's refusal record crashes or reports an unclassified error instead. Fix: wrap `ObjectStore.open` and every pack read in a catch that converts to `invalid-pack-index` / `corrupt-object`, and range-check offsets against the pack size before reading. Add a test for each.

2. (revise) Symlinks and non-regular files under `objects/` are followed. That allows a hang and a de facto alternate. Only `gitDir` itself is `lstat`ed (line 188). [Observed] PoC `fifo`: a loose-object path symlinked to a FIFO blocks `readBlobs` indefinitely ("still blocked after 5s"). No refusal is ever made, so the step neither completes nor refuses. [Observed] PoC `idxdir`, third case: a clone whose `objects` is a symlink to another store's `objects` directory reads successfully. Functionally that is an alternate the reader follows. The bytes are still hash-verified, so integrity holds [Inferred]. But 033 says an object "that cannot be read without an alternate … SHALL refuse", and the read is of a file outside the clone, possibly another repository's store, which matters under per-repository consent [Inferred]. [Inferred] A symlink to `/dev/zero` or another device behaves similarly (unbounded `readFile`). Fix: refuse unless `objects/`, `objects/pack/`, each loose file, `.idx` and `.pack` are regular files or directories reached without a symlink (`lstat` plus `O_NOFOLLOW` on open, and `isFile()` before reading). Add FIFO and symlinked-`objects` tests.

3. (revise) Tree-entry name hygiene: `listTree` emits paths that `readBlobs` refuses or reads ambiguously. `parseTree` (lines 156-168) rejects only an empty name and `/`. [Observed] PoC `names`: a hash-valid tree with entries `..`, `.`, `.git` and two entries both named `dup` makes `listTree` return the paths `..`, `.`, `.git`, `dup`, `dup` with different ids. `readBlobs(['dup'])` returns the first entry's blob (line 122 `find`), and `readBlobs(['..'])` refuses `malformed-path`. [Observed] Two names that differ only in invalid UTF-8 bytes (`a\xff`, `a\xfe`) both decode to `a�` (line 162 decodes utf8 lossily), so the path-to-blob mapping is ambiguous. These objects can only come from the upstream repository, because they are reachable from the consented commit and hash-checked [Inferred]. But a public upstream is untrusted content. A downstream S3+ consumer that writes source pages by path, or anchors a quotation by path, inherits `..` traversal and duplicate-path ambiguity. git's `fsck` treats `hasDot`, `hasDotdot`, `hasDotgit`, `duplicateEntries` and `treeNotSorted` as errors [Inferred, general knowledge]. Fix: refuse `malformed-tree` for `.`, `..`, `.git` (case-folded), duplicate names, invalid UTF-8 (or carry raw name bytes), and out-of-order entries. At minimum, `listTree` must never emit a path that `readBlobs` would refuse or resolve to a different entry.

4. (revise) Total work per call is unbounded within the per-object and chain caps. `maxObjectBytes` (default 1 GiB, line 83) bounds one inflate or delta result, and `MAX_DELTA_CHAIN` (10,000, line 171) bounds depth. Nothing bounds their product or the sum over a call. [Observed] PoC `amp`: a 269,162-byte pack whose `.idx` points the pinned blob id at the top of a 100-deep offset-delta chain, each level copying a 256 MiB base, ran 19.34 s and peaked at 1.12 GB RSS before refusing `identifier-mismatch`. At 16 MiB per level, 50 levels took 314 ms and 200 levels 859 ms. [Inferred] Linear extrapolation to the allowed 10,000 levels at 1 GiB is on the order of two hours of synchronous CPU (`inflateSync`, line 283) plus several GB of memory, from a pack of a few MB that any agent session can write. The step eventually refuses, so 033 is not violated as written, but a trust-boundary reader should fail fast. Fix: add a per-call budget of inflated plus delta-output bytes, lower the chain cap (git's `pack-objects --depth` is capped at 4095 [Inferred, general knowledge]; real chains are usually ≤ 50), and test both bounds. The PR description's "Delta bounds" paragraph should state what is not bounded.

7. (note) Fail-closed denial of service by the agent is inherent, and is acceptable under 033 as written. [Observed] Loose objects are preferred (line 216-217), so a planted corrupt loose copy refuses even when a valid packed copy exists. Any junk `.idx` refuses every read, including all-loose stores (PoC `idxdir`: `invalid-pack-index … bad header`). This is consistent with "refuse the step", but the run record should not attribute such a refusal to the upstream repository. Wording for S3.

8. (note) The refusal message carries a digest of the refused bytes: `the object read as X hashes to Y` (line 209; asserted at test.ts:157). A digest is not content, but the class comment says the refusal carries "none of the refused object's content" (line 25), and 033 says none of it "SHALL be used". [Inferred] Harmless for confidentiality, because the agent shares the user. Either drop `actual` from the message or state in the doc comment that a digest is carried.

9. (note) SHA-1 is checked without collision detection. `createHash('sha1')` (line 208) is plain SHA-1; git uses sha1dc, which rejects known collision-attack shapes [Inferred, general knowledge]. Chosen-prefix collisions need the attacker to control both colliding objects before the upstream publishes one, so this matters only if an upstream author colludes with the agent session. Disclose it, or prefer SHA-256 identifiers where the consent allows.

10. (note) Huge and pathological trees. `list` (lines 136-144) re-walks shared subtrees once per reference. The per-call cache (line 147) avoids re-hashing but not re-emitting, so an upstream tree DAG with repeated subtrees yields output exponential in depth [Inferred]. `readBlobs` has no aggregate byte cap. Each call also re-reads and re-parses every `.idx` in full (line 194), which [Inferred] will dominate cost on a large clone if S3 calls per quotation. Note the cost model for S3.

11. (note) Mode handling is permissive but safe. [Observed] Any 5–6 digit octal mode passes (line 163). A non-canonical `040000` is treated as a file: intermediate segments refuse `path-not-found` and the last segment refuses `type-mismatch`, through `verified`. A gitlink is listed with mode `160000` and its commit id (test.ts:273) and refused by `readBlobs` (line 130). Callers of `listTree` must not treat every entry as a readable blob; say so in the `listTree` doc comment.
