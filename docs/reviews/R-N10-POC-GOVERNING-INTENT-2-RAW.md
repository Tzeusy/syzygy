## Findings

**Finding 1 — The Trajectory arms of the oracle contradict signed POC-REQ-042's bounded board** (revise)
POC-REQ-014's Oracle: "Trajectory's narrowed board lists exactly the enumerated items", where the enumerated items are "every served work item from the machine answer — the denominator is the complete served item set (POC-REQ-011)". The Required behavior says "Trajectory SHALL mark each such item" and Scenario 1 says "Trajectory marks all N". But signed POC-REQ-042 makes Trajectory render a *selection*: "Trajectory SHALL visibly declare which work-item population it renders (its selection rule) and the counts inside and outside that selection", with the scenario "the database holds 6,964 items and Trajectory renders a selection of 192". [Observed in code at the reviewed commit, as context only: `routes.ts:233` serves `JSON.stringify(model)` as the machine answer, and `trajectory-projection.ts:109-112` renders "all non-closed items, plus the N most recently closed items" with `excludedCount: workItems.items.length - rendered.length`.] Since every served item carries the Unknown, narrowing removes nothing, so the narrowed board equals the bounded board, which is a strict subset of the served set whenever the excluded count is non-zero. Any implementation that satisfies POC-REQ-042 over Butlers (about 7,958 rows) fails POC-REQ-014's oracle and Scenario 1; one that satisfies POC-REQ-014 violates POC-REQ-042's selection. The delta's own *Denominator* paragraph cites POC-REQ-042 without noticing this. State the Trajectory arms over Trajectory's rendered selection (marked items and narrowed list equal the rendered set; the Unknown count disclosed against both the rendered and the excluded counts), or say how the narrowed view relates to the excluded population; then re-judge the RFC8-23 "filterable" covered row against the repaired oracle.

**Finding 2 — The oracle still does not decide several obligations the requirement and the covered rows claim** (revise)
The Oracle decides `governedBy` value/reason/route, the count equalities, the narrowed list, and the fixture item. It does not decide: (a) "Trajectory SHALL mark each such item" (per-item Unknown marker); (b) "state beside it that an item is resolved by supplying its warrant" (the resolution sentence); (c) "Every such item SHALL render with its Unknown marker, never as warranted, green or complete". The Observable lists (a) and (b) and the Falsifier lists (b) and (c) ("no resolution sentence"; "an item rendered as warranted, green or complete"), so a checker following the Oracle as written passes a surface that has neither marker nor sentence and renders items green. CC-SPEC-4 requires an "effective success/failure oracle … how one decides the observation IS (or is not) the expected one, by a stated procedure"; round-1 Finding 1 was this same class for the reason. The RFC8-23 covered row ("counted, filterable and never green, its route resolvable by supplying a warrant") and the RFC8-24 covered row ("with its route visible") rest on (b) and (c), which only the falsifier names — so criterion 3's "claim only what POC-REQ-014's oracle observes" is not met for those limbs. Add the marker, the sentence and the non-green encoding to the Oracle with a stated decision procedure (e.g. the rendered encoding equals the machine answer's Unknown, as POC-REQ-043 does), or narrow the covered rows.

**Finding 3 — RFC8-24, newly mapped, has two unlisted limbs** (revise)
RFC8-24 continues after its reason list: "Unknown aggregation follows RFC2-24's rendering rule: aggregate, disclose reason counts, expand. **These are claim reasons only:** the normalized state's four absence values are state-local, take no reason from this list, and are counted separately — an aggregate of Unknowns never absorbs them (RFC8-12; RFC6-6)." POC-REQ-014 serves exactly such an aggregate (the "N of N" Unknown count), yet the matrix has no row for the aggregation rule (aggregate / disclose reason counts / expand) and none for the claim-reasons-only / no-absorption limb. The two RFC8-24 rows cover the reason with its route and list the other four reasons plus the retention event as Unknown. Criterion 3 requires "every uncovered limb of a newly mapped clause is listed as Unknown"; add a row for each (covered only as far as the oracle observes the count, Unknown for reason-count disclosure, expansion and the state-local separation).
