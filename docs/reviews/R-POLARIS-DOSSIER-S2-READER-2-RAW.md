## Findings

1. (revise) [Observed] The per-call work bound can be evaded by padding stored bytes. Only *inflated* bytes are charged (`charge` at git-object-reader.ts:373, 320, 469). The compressed input a call reads and inflates is neither charged nor capped. `inflateAt` (372-385) starts at `storedBound(size)` and then **doubles its window up to the end of the pack**, re-reading and re-inflating from the start each time. A zlib stream may carry any number of empty non-final stored blocks and still inflate to exactly the declared bytes, so a padded entry still verifies. Offset and reference deltas cache no base, so many objects can share one padded base, and every read re-inflates it.

   Probe `pad 50 268435456`: one 256 MiB padded base and 50 distinct blobs, each an offset delta over it. `readBlobs` of all 50 returns 50 verified blobs in 51.8 s (56.4 s CPU, 746 MiB RSS). With `maxInflatedBytesPerCall: 1 MiB` it still returns all 50, in 51.6 s. One blob alone takes 1.06 s at 696 MiB RSS. Probe `loosepad 20 134217728` gives the same result with a 128 MiB padded *loose* base under 20 reference deltas: all 20 returned in 6.9 s under a 1 MiB call budget.

   [Inferred] The work is linear in objects × padding. Disk holds the padding once, and the only ceiling is `maxObjectsPerCall` (1,000,000, two counts per delta object). Reading a few hundred sources over a 1 GiB padded base therefore costs on the order of tens of minutes per call. Memory is not bounded by `maxObjectBytes` either: `readAt` allocates the doubled window, up to the pack's size (377, 423-427).

   The header comment says the reader "bounds each call" (25-27), and the PR body's "Bounds per call" names `.idx` bytes as the only unbounded cost, so both overstate. Fix: git writes zlib streams no larger than `storedBound(size)`, so refuse `corrupt-object` instead of doubling past it. Charge the stored bytes read, loose and packed, to the call budget, and cap a loose object at `storedBound` of its own inflated size once that size is known. Add a padded-stream test and mutants for each.

2. (revise) [Observed] Regression: a legitimate tree with a large subdirectory is refused as a store fault. `list` builds its result with `out.push(...await this.list(e.id, p))` (183). Once a subtree yields more entries than V8 accepts as call arguments, this throws `RangeError`, and `step` (117-119) relabels it `store-unreadable`. Probe `wide 200000`: a root tree with 200,000 entries lists in 307 ms, but the same 200,000 entries one directory down refuse `{"reason":"store-unreadable",…,"message":"the object store could not be read (RangeError)"}`. That is far under the 1,000,000 cap, and the store is valid.

   [Inferred] The threshold is V8's argument limit, on the order of 10^5. A large monorepo crosses it under any directory holding that many descendant files (vendored third-party trees, for example), and the refusal blames the clone for a reader bug. Butlers is far below it. Fix: append in a loop, or pass one accumulator down the recursion. Add a test above the threshold.

3. (note) [Observed] The comment overstates the name hygiene. It says the reader refuses "a tree entry git's fsck rejects as ambiguous" (23). Probe `dotgit` shows that `listTree` accepts and returns `.git‌`, `.g‍it`, `git~1`, `GIT~1`, `.git.`, `.git ` and `.git::$INDEX_ALLOCATION`. [Inferred, general knowledge] git's fsck also flags the HFS+ ignorable-code-point and NTFS spellings as `.git` (`is_hfs_dotgit`, `is_ntfs_dotgit`, after CVE-2014-9390). Out-of-order entries are still not refused, and the PR discloses that. Within this reader paths stay unambiguous, because names are exact byte strings and duplicates are refused. The exposure is a later consumer that writes these paths to a case-folding or normalising filesystem. Either narrow the comment to what is checked, or refuse those spellings too.

4. (note) [Inferred, from reading 307-308, 254-260 and 401-421] The disclosed lstat-to-open race allows nothing beyond re-hashed bytes, plus two small effects that should be named.
   - **What the race reaches.** Swapping `objects/`, `objects/pack/` or a fan-out directory for a link after its `lstat` makes the following `open` (or the `readdir` at 255) resolve through the link. `O_NOFOLLOW` guards only the last component.
   - **Why returned content is safe.** What is opened must still be a regular file (419). Loose files are capped at `storedBound(maxObjectBytes)` (311). The file name is fixed by the identifier's hex, or must end `.idx`, so no device node can be named. Anything returned must hash to the identifier the consented commit reached. Returned content is therefore identical to what the clone itself would supply.
   - **What is beyond.** (a) The reader can be made to read a regular file outside the clone into memory: up to about 1.125 GiB for a loose object, an `.idx` in full, or a `.pack` windowed. (b) The refusal reason (`corrupt-object` for a failed inflate or header versus `identifier-mismatch`) is a coarse oracle on whether that file is a zlib object. The agent session runs as the same user and could read such files directly, so neither adds capability.
   - **Hardlinks.** A hardlinked loose object (not caught by `O_NOFOLLOW`) has the same effect with no race at all. The "follows no symbolic link" wording is accurate, but "nothing under .git is read through a link" (404) does not cover hardlinks.
   - **Hardening.** Optional: compare `fh.stat()` dev and inode against an `lstat` taken after opening, or check `/proc/self/fd` realpath containment on Linux.

5. (note) [Observed] Splitting work across calls is in the caller's hands, not the store author's. Every budget lives on the per-call `ObjectStore` (238-239, 114), and the reader object keeps nothing between calls, as 033's re-read rule requires. A `readBlobs` list is charged as one call (`budget-sum` test, test.ts:571-576). A tree DAG's fan-out is charged per listed entry (`count` at 182; the `dag` test at test.ts:590-599 lists 65,536 paths from five objects and refuses at a 10,000 cap). The store's author cannot raise the number of calls. S3 makes one call per quotation, so a run-level ceiling belongs to S3; the header comment should say the bounds are per call only.
