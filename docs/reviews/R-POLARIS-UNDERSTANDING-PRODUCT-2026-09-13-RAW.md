# Independent product/spec review: Polaris project understanding

Review date: 2026-09-13. Discussion-draft review only; no adoption verdict or
implementation authorization. Review context was the four product artifacts,
VIS-1 through VIS-4, trust-and-evidence, and adopted generator requirements
001–006, 009, 014, 019, 020 and 025. No implementation inspection or full contract
census was performed. Implementation-status statements in the packet were not
independently verified by this review.

## Assessment

[Inferred] The packet offers a meaningful research-to-understanding-to-clarification-
to-argument-to-artifact-to-independent-review product loop. Its scenarios distinguish
unsupported intent from implementation evidence, partial usefulness from completion,
and genuine reader evidence from stage integration. It correctly preserves existing
006/014 obligations, admits no new source permission, and avoids a diagram quota or
numeric understanding score. It is useful for product discussion with the following
clarifications; it is not an exact amendment offer.

## Findings

1. **Material ambiguity: editorial freedom versus mandatory reading structure.**
   SPEC-DELTA D4 says composition must not "force a universal section list" and
   VISION makes shape follow the project. Adopted 004 nevertheless requires the
   primary altitude order unless the owner rules otherwise, and default
   argument/contract/reality bands with their actual content obligations. The
   blanket preservation statement does not tell a future implementer how these
   interact. State that project-specific argument, headings and assets vary within
   the retained required altitudes/bands, or identify a separate proposed change
   if freedom beyond them is intended. Add a case in which a compelling library
   narrative cannot silently omit catalog, exact-leaf access or honest empty bands.

2. **Material evaluation gap: new owner answers arrive after the oracle freezes.**
   EVALUATION freezes acceptable answers directly from admitted sources before
   generation; D3 then introduces previously undocumented purpose through owner
   clarification. It explains later source-based evaluator corrections, but not
   this intended change to the evaluated premises. Specify that a newly admitted,
   attributed answer extends the case inputs and triggers an independently frozen
   affected oracle revision before the revised candidate is judged. Preserve the
   earlier unknown outcome and original oracle. Add a counterexample where the
   generated thesis misstates the owner's answer: approval of the answer or reuse
   of the question ID must not make that thesis pass. This keeps the interview
   path evaluable without allowing the authoring output to rewrite its own target.

## Actionable next design questions

- What is the first supported repository profile, including document/code forms,
  project-boundary declaration and finite scale? The broad direction is clear;
  choose one concrete profile to make the discovery prototype falsifiable.
- Who fixes the evaluated project boundary before discovery, and how is a proposed
  narrowing presented? D1 properly identifies source-scope changes, but a case
  should show that narrowing around an awkward component retires the old coverage
  claim and cannot count as success on the original requested scope.
- README calls the default "interview-first" although VISION consistently says
  investigate first. Name the choice "clarify before a confident thesis" versus
  "qualified draft before clarification" so it does not imply interviewing before
  available evidence has been investigated.

These questions do not require an approval ceremony to continue design discussion.
They do require explicit answers before treating the relevant proposed behaviors
as precise implementation contracts.
