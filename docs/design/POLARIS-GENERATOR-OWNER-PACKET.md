# Generalized Polaris generator — owner package preparation

Working packet, not yet offered for approval. Candidate source and evidence must
be frozen and final independent specification/authority reviews must pass before
an approval phrase is offered. No approval is inferred from the active goal.

## The outcome this package enables

A reusable LLM-assisted process generates a project's manifesto from admitted
sources, with meaningful diagrams and optional deep dives, then checks and repairs
its output. Polaris provides the complete start/progress/review experience.
The same code, prompts, validators and renderer must work on two real projects
and regenerate after real source changes. Butlers is one proving case.

The implementation replaces per-project compiled offsets as the generation
mechanism. It preserves the existing Butlers observer and reading surface through
an explicit adapter. Generic source ingestion, structured drafts and safe preview
are separate reusable components, not a clone of the Butlers page.

The specification remains candidate until the actual owner act. The scope

matrix is not any of those acts.

## Concrete implementation boundary

Use a project-neutral core, immutable source/draft/review bundles, bounded provider
and persistence adapters, and a trusted bundle renderer. Reuse existing citation,
safe-Markdown, layout and browser-check primitives where their contracts fit.

The new generator uses a separate local process/origin and scoped credentials;
legacy PWB tokens and open routes grant no generator rights. A narrow protected
recorder lives outside governed repositories and untrusted write reach, with
separate service/supervisor roles and actual tampering/recovery tests. Browser
pairing requires fresh owner-attended confirmation, not machine authentication.
No observed-project code is executed and no competing work queue is created.

Source/provider/write effects remain separately admitted. Implementation approval
alone sends no project content to a provider, reads no second repository, grants
no new destination write and enables no production release or broad remote mode.
The supported-profile boundary cannot manufacture worker activity from model
receipts or silently omit a real staleness bound.

## Required evidence before calling the goal done

- Actual source-to-model-to-bundle-to-preview runs, not fixture-only output.
- Independent full-source fidelity and cold-reader/visual judgments over frozen
  generated pages, including middle sections and optional depth.
- Meaningful diagrams whose nodes and factual edges have support; material
  qualifications, Unknowns and exact-source access remain usable.
- Working start, progress, cancel, resume, review and repair, with real failure
  and uncertain-effect cases distinguished from success.
- Unchanged code/prompt/schema/renderer identities across two admitted projects.
- A real changed-source run updating dependent prose, diagrams, glossary, deep
  dives and links, with obsolete reviews invalidated.
- Required counterexamples, protected-boundary evidence, compatibility checks,
  final clone/CI validation and a requirement-by-requirement completion audit.

## Why the specification approval is a real boundary

The repository's operating instructions require an authorizing act before
implementation outside existing scope. RFC7-38 requires approved OpenSpec
coverage or effective reviewed non-applicability for the observable consequences
of the narrative contract. Existing PWB implementation authority is bounded to
its signed change and does not provide the broader generator/provider/project
permissions. The active product goal authorizes preparing this concrete package;
it does not itself adopt unseen specification bytes or grant unnamed data routes.
