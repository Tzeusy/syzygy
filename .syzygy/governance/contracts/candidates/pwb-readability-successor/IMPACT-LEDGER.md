## Overlap with other PWB packages

[Observed] Eight tracked packages carry a `spec.md.patch` for the same
`spec.md`. The builder classifies each by searching every hunk's old and new
text in the current spec: **7** are applied (opening band, exact-source render
mode, machine view, missing currency, dismissal expiry, container shape, item
depth), **1** is declined and never applied (the lane B scoped-attributes
package) and **0** are pending. A patch that is none of these fails the
check, so a new sibling cannot be skipped silently. A pending sibling would
fail it too: this restyle rewrites every requirement block, so it has to be
drafted last.

This package asserts no successor-chain position beyond being drafted over
the latest signed version.

## Failure and regeneration boundary

`scripts/build_pwb_readability_successor.py` fails closed when:

- the patch target set is not exactly the four subjects above, or a patch no
  longer applies;
- the predecessor differs from the item-depth v1.0 manifest rows;
- a requirement, scenario, warrant, modal or normalized word moves, or a
  label leaves the closed set;
- the guide loses its non-normative statement or names a wrong title;
- a quoted fragment another script or coverage row relies on disappears;
- the generated dependencies, coverage or manifest drift;
- the semantic map misses a unit, misclassifies a requirement or scenario, or
  misstates its count;
- a sibling spec patch is neither applied nor declined.

`--write` is deterministic and writes only the candidate's dependency patch
and manifest; `--check` and `--diff` are read-only. `--apply --at-adoption`
writes the four signed subjects, refuses without the flag, and refuses unless
the whole package verifies, so a failed check leaves every signed byte
unchanged; `scripts/record_versioned_signoff.py` is its only caller.
