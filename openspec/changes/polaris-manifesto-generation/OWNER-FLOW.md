# Requesting a manifesto — candidate flow

Proposed owner experience for REQ-polaris-generation-020. This describes the
future application, not authority to perform any of these operations now.

## Open the project and choose the outcome

The owner opens Polaris and chooses to generate or refresh the project's
manifesto. The application resolves the selected project's declared governance
root and authorized work/artifact homes; it does not infer writable locations
from the observed source repository. Missing or conflicting declarations remain
explicit setup failures, with the available honest project view still readable.

The request uses known project context and an effective preset where available.
The owner sees the purpose of the run, source scope, provider, spending/time
bounds and requested assets in ordinary language. Technical identifiers and
supporting records are reachable in detail; the start screen does not require
copying paths, writing manifests, finding scheduler identifiers or re-entering
still-effective consent. Unknown prerequisites are named rather than defaulted.

The start flow needs no model call to prepare its own authorization. Initial
preparation uses admitted metadata, the owner's requested outcome and the
existing policies/requirements. It neither reads additional project bodies nor
sends data to a provider to discover whether sending data is permitted. Draft
effect plans can be shown transiently before write permission; persisting a
proposal or request record requires its own effective write authority.

## Resolve warranted work

The application checks for an existing, explicitly reusable work binding covering
this project, requested purpose, pinned warranted intent revision and effect
scope. It validates its immutable materialization record, current scheduler
eligibility, remaining authorized allowance and applicable approvals. A matching title or old successful run is
not a match. If several candidates remain and the effective policy does not
select one unambiguously, show the meaningful choices; do not choose the newest
record or merge incompatible proposals. A new regeneration cannot reuse an
exhausted or narrower authorization or rewrite an existing pinned warrant.

When no reusable binding exists, the application prepares the execution-intent
Proposal and effect plan for the owner. The plan makes requested source/provider,
storage, scheduler and budget effects concrete. It records what existing authority
covers and which approvals are missing. Preparation is not approval. A prior
Decision may cover the exact new work only when its recorded scope says so;
child proposals inherit approval only when the parent's Decision explicitly
permits it. No standing approval is invented to make the flow shorter.

The owner completes any genuinely missing approval through its existing gate.
The application supplies the records and context; the owner does not assemble
governance files or scheduler commands. A generic Generate action is not silently
interpreted as a missing specification, policy, provider-consent or execution
approval. Once required authority is effective, the same request continues from
its recorded state without asking again for unchanged approvals.

## Materialize once, then execute

The approved execution-intent Proposal keeps its identity. A recorded
queued-for-materialization fact is not a new kernel state and is not labelled
scheduled. The application uses the project's registered scheduler adapter for
the authorized creation/reuse operation. The durable materialization record
binds proposal identity, scheduler-issued work-item identity set and the exact
warranted intent revision; the materializing evaluation is retained alongside.

The written record is the transition boundary. Before it exists, the Proposal
remains authoritative for planned work. After it exists, the scheduler owns work
lifecycle and the Proposal is terminal materialized. Only then may the existing
dispatch-admission protocol evaluate and reserve a provider attempt. No stage
skips the record because scheduler creation returned success.

If scheduler creation succeeded but recording failed, show the orphaned-work
Contradiction and keep its affected conclusion Unknown. Never silently create a
replacement, fill in the missing record, delete the orphan or send a provider
request. Recovery follows owner adjudication; an authorized re-materialization
cites and supersedes the finding. Duplicate start/request identities return the
same preparation, Proposal and materialization outcome or an explicit conflict,
never independent scheduler creations. Creation has a stable operation identity
and exclusive durable claim before the scheduler call; duplicate callers cannot
both create. Supported idempotency or authoritative lookup may establish an
existing result, but no such substrate capability is presumed. An uncertain scheduler effect is retained
as uncertain and is not automatically retried. If enumeration observes an item
without its record, calling it materialization in progress cannot hide the
required orphan finding. Ordinary editorial stages remain subordinate run
metadata; they do not require a child Proposal or work item for every model call.

## Follow the draft through review

The owner sees preparation, missing approval, queued-for-materialization,
generation stage, review, repair and ready-for-owner as their correctly qualified
states. These stages do not become normalized scheduler or intent-reconciliation
states. Progress and recoverable errors are visible; returning to the project
restores the identified request and its actual next step.

Cancellation before dispatch admission prevents new provider effects under the
existing ordering rule. It does not erase already prepared or materialized work:
scheduler lifecycle changes use the scheduler adapter and their own authority,
while historical records remain. During execution, late effects, usage and
partial results follow the existing cancellation/recovery contract.

Successful generation produces a reviewed editorial candidate. The owner can
read it as a coherent manifesto, inspect meaningful changes and sources, and
perform applicable per-block authorship acts. An unsigned profile, failed review
or unresolved required asset remains explicit. A completed work item, model
response or generic start action never adopts the narrative or establishes
product comprehension. Regeneration preserves the previous authored version
until the authorized replacement is actually applied.
