# Candidate generator interfaces and ownership

Proposed interface decisions for review. This is not an accepted schema or an
adapter registration. The specification owns observable behavior; existing
identity, act, source-state and namespace contracts remain controlling.

## Boundary model

The generator has no filesystem crawler, shell tool or implicit network route.
Acquisition supplies an identified bundle; an admission service resolves its
permissions independently; a provider adapter dispatches bounded content; the
lifecycle adapter records execution; the artifact adapter performs separately
consented writes. Model output can request missing information as a finding, but
cannot invoke any of these interfaces or supply permission state.

SCHEMA-CONTRACT.md defines record ownership, requested/produced variants, identity
issuance, typed anchors, reference integrity and version behavior.

SOURCE-POLICY.md specifies consent granularity, provenance-derived classification,
every-ingest screening and the distinct whole-artifact/partial-redaction outcomes.

The proposed versioned interchange is structured data with explicit variants.
Unknown variants/versions and extra effect-bearing fields are refused. Content
and diagnostic byte limits apply before parsing or persistence.

ASSET-CONTRACT.md defines the proposed closed asset kinds, their record content,
reviewable omissions and curated/computed boundary. A computed reference retains
its owning renderer's obligations; it is not an arbitrary embed or permission to
activate deferred live transclusion. Required unsupported assets stay unresolved.

Generation provenance distinguishes requested model identity from provider-reported
identity/version. An unavailable provider revision is explicitly unreported, never
filled from an assumption about an alias. The declared reproducibility standard
is recipe replay from retained permitted inputs; generated bytes are not promised
identical. A policy requiring a reproducibility guarantee the provider cannot
supply refuses that route explicitly.

These records do not mint new global epistemic values. Run progress, profile
state, editorial-draft/curated state and underlying source claims are separately
queryable. The source inventory is review evidence, not adopted project intent.

SECURITY-CONTRACT.md defines caller admission, per-operation authorization,
protected audit and immediate revocation behavior. A successful scheduler
observation or local commitment never replaces these effect-boundary checks.

NAVIGATION-CONTRACT.md defines shared selection, scenario, drawer and query

admission. Presentation hints and disclosure depth never create another fact set.

WORK-STATE-CONTRACT.md separates recorded generation progress from normalized

signal derivation case remains an explicit conformance decision, not a fallback.

## Effect interfaces

- **Admission:** Given project, source snapshot, provider/content class or write
  destination and evaluation instant, return the existing permission evaluation
  with its exact provenance and refusal reasons. The generator cannot supply an
  override. Acquisition integrity is checked against the owning records: changing
  claim text while retaining a legitimate source reference is not a valid bundle. Re-evaluation occurs before dispatch, resume, adoption and export.
- **Provider:** Accept a reserved attempt identity, admitted content and hard
  request/output bounds. Return screened-candidate input plus usage/dispatch
  receipts. Tool/function requests in output are not executed. A provider without
  a usable bound or permission cannot be selected silently as a fallback.
- **Lifecycle:** Scheduler mutations use the scheduler's typed adapter,
  synchronously and attributed, followed by a re-read. Separately, conditional
  execution-control writes compare an execution-control revision and append one
  identified run/attempt event. An already-applied event is returned as such;
  a changed revision is a conflict. Scheduler revisions and control revisions
  are distinct fields. No independent generator queue exists under intent or
  in a private task database.
- **Artifact:** Read/write an identified projection or authored artifact through
  its proper home and consent. Authored changes use expected-predecessor comparison,
  atomic replacement and attributed reversal; they never overwrite unfamiliar
  authored bytes as a cache refresh.

ADAPTER-DECLARATIONS.md specifies the adapter registration fields, ownership,
failure mapping and complete run envelope that stage artifacts do not replace.
The corresponding registry entries and schema placement still require their
applicable review and effective acts before operational admission. These
interfaces select separation of responsibilities, not a storage engine or SDK.

OWNER-FLOW.md defines request preparation, exact work reuse, missing-approval
handling and materialization before this dispatch protocol. A caller is not
required to assemble the work records manually.

## Budget and retry decisions

Each run supplies positive finite `maxCalls`, `maxInputBytes`, `maxOutputBytes`,
`maxUsageUnits` and `maxElapsedMs`, plus finite nonnegative `maxRepairCycles`,
with a versioned accounting
unit/policy reference. There is no implicit unlimited value or agent-selected
spending default. The UI can prefill an effective owner-approved preset and
show its bounds before start; ordinary runs do not require re-entering technical
limits or re-granting still-effective consent. The policy maps provider limits to worst-case reservations;
unbounded or unknown required accounting refuses that provider dispatch.

The original start and absolute deadline are durable. Downtime consumes elapsed
budget and resume cannot extend the deadline. Reservations and actual receipts
are distinct; a missing final receipt is uncertain usage, not zero. Late receipts
are attached to their original attempt even after cancellation. A new retry
decision must identify the uncertain prior attempt and explicitly reserve its
maximum additional cost; it never rewrites the earlier uncertainty as absence.

Execution event proposals include request identity, attempt identity, expected
execution-control revision, separately identified scheduler observation/revision,
and artifact digests. The adapter's conditional write determines
which competing event applies. Accepted cancellation/rejection before authored-write commitment prevents a
later stage-success event from making a draft ready. Late requests after that
commitment are reported as too late, not falsely acknowledged as cancellation. A failed conditional update is
reported and reconciled from the authoritative work record, not retried blindly.

## Durable dispatch reservation

The registered lifecycle adapter is the sole writer of run-budget reservations
and dispatch claims in their declared execution-control record. This is not
ownership of scheduler lifecycle: after materialization scheduler fields are
read from the scheduler at the answering evaluation and are never mirrored as
editable generator fields. Both surfaces are projections of those owning records.
Execution-control schemas must identify their field ownership explicitly before
registration; they cannot redefine scheduler state or the immutable materialization
join. They are subordinate metadata of the existing Execution run and Execution
Record identities (RFC8-4), not new kernel entities. A reservation requires the
valid immutable materialization join and applicable warranted execution authority;
an orphan finding blocks dispatch pending owner adjudication. Before a provider
call, the execution-control transaction atomically compares its own control
revision, request/stage identity, cancellation/rejection state, original deadline
and remaining budget, then records one reserved attempt and its maximum charge.
Only a successful durable reservation can proceed. Competing callers cannot both
reserve the same stage or spend the same allowance; losers receive the existing
attempt or an explicit conflict without contacting the provider.

A reserved attempt becomes dispatching through a second conditional transition
that grants exactly one dispatcher the attempt. Fresh admission is checked at the
effect boundary; failure before dispatch records a known refusal. No network call
is legal before the dispatching transition is durable. A crash after that point
is conservatively uncertain even if it happened just before the network call.
Lease expiry is not permission to send the attempt again.

An uncertain reservation continues to consume its reserved availability until a
trusted receipt or effect-and-usage resolution establishes the actual effect and usage. Recovery
never infers no effect from a missing response or missing file. A known unsent
reservation can be released through the lifecycle adapter; an uncertain effect
requires authoritative effect-and-usage resolution or an explicit new bounded retry attempt.
The new attempt references the old uncertainty and cannot silently reuse its
allowance. No automatic new run resets budgets to evade the original bound.

### Dispatch admission and scheduler observation

A dispatch admission is the durable transition from reserved to dispatching. It
is the ordering point for accepted local cancellation and exclusive ownership,
not proof that a provider received bytes. From that point the attempt is
potentially in flight, including the crash window before the network call.
Reservation alone is not admission. A cancellation that wins before admission
prevents it; one that follows admission prevents later admissions and attempts
supported cancellation of the admitted effect without claiming it stopped.

For every admission, including a retry or resumed reservation:

1. Read the scheduler through its registered adapter in a new admission
   evaluation. Bind the work-item identity, scheduler revision, capture instant
   and evaluation to an immutable observation reference. Validate the existing
   materialization join and execution warrant at that evaluation. Missing,
   withdrawn, superseded, ineligible or unavailable required scheduler state
   refuses admission; a last-good permissive projection cannot authorize it.
2. Evaluate the applicable consent and effect permissions through their own
   authority service. A scheduler observation never stands in for provider or
   content consent. Recheck these permissions at the provider effect boundary.
3. In the execution-control transaction, compare the expected control revision,
   original deadline, remaining allowance and accepted cancellation/rejection
   disposition. Verify the observation is still within the declared admission
   freshness bound; a future-dated or expired observation is refused. Bind it
   to this attempt and atomically grant one dispatcher exclusive ownership.
4. Initiate the single bounded provider attempt through the provider adapter.
   A known refusal before sending is recorded without a provider charge; lack
   of proof that nothing was sent remains an uncertain reserved effect. Neither
   expiry of dispatch ownership nor process recovery grants permission to send
   the same admitted attempt again.

The transaction is atomic over execution control only. Scheduler state may
change after capture, even before physical transmission. The record means
eligible at the named admission evaluation, never guaranteed unchanged through
provider completion. It stores historical evidence, not an editable copy of
current scheduler state. No scheduler mutation is required just to observe
eligibility; offered mutations still use its attributed adapter and re-read.

Every later stage admission and each transition to ready or authored-write
commitment re-observes the scheduler under the same eligibility/freshness check.
When withdrawal or
supersession is subsequently observed, the control service blocks further
admissions, readiness and not-yet-committed finalization, attempts supported cancellation of
admitted operations, and records outcomes and late usage without changing the
materialization join. An authored-write commitment already made retains its
existing ordering semantics; a subsequent request cannot falsely claim reversal.
An admitted operation may have completed; report that
fact rather than rewriting it as cancelled. Resume cannot use a previous
permissive observation or an old local plan to bypass this check.

This selects an observation-based scheduler guarantee under RFC4-5/15 and
RFC8-7/9/10. It does not weaken consent-revocation enforcement or promise
instantaneous detection of external scheduler changes. Adapter declarations
must expose the observation/freshness behavior, source failures and provider
cancellation support; implementation tests exercise the boundary directly.

## Authored-write commitment and receipt recovery

The lifecycle adapter also serializes cancellation/rejection against finalization.
After valid per-block owner-act evaluation, current write admission, exact bundle
review checks and predecessor identification, one conditional operation records
an authored-write commitment. It references the governing owner act, immutable
bundle, destination, expected predecessor and a unique finalization identity;
it contains no narrative body and is not a second copy of the owner act.

This commitment is the ordering boundary. If accepted cancellation/rejection
wins first, commitment is refused and no authored write is dispatched. If the
commitment wins first, a later cancellation/rejection request reports too late
and the current finalization state; it must not claim the run was cancelled or
the artifact undone. Reversal is a separate consented, attributed action.
Commitment is not evidence that the artifact has been written or adopted on the
surface: that state waits for verified application of the authorized write.

The artifact adapter consumes the unique finalization identity idempotently,
rechecks applicable write permission at the effect boundary, and atomically
records the resulting artifact/version and application receipt together. The
receipt binds finalization identity, owner-act reference, exact written digest
and predecessor. It is durable in the owning artifact's version/receipt home,
not in a competing work queue. A consent failure or conflicting predecessor is
an explicit refused finalization; commitment cannot override those gates.

If the write succeeds but its work acknowledgment is lost, recovery reads that
receipt and reconciles the work projection without another write or act. If the
artifact was subsequently edited by a human, recovery reports the applied
version and the newer state; it cannot restore the old bytes over the new edit.
Absent or expired receipts do not prove non-application: unresolved finalization
remains uncertain and requires receipt recovery or authoritative effect resolution. Receipt retention must cover the
policy's recovery horizon; after that horizon automated replay is unavailable.

## Retention decisions

Generation requires an effective project retention policy naming bounded expiry
for draft projections and expirable raw execution detail, permitted storage homes
and deletion behavior. Missing policy refuses durable generation. Policy inputs
cannot remove RFC8-26's preservation set or override another artifact's governing
retention obligations.

- Expired or rejected drafts cease to appear in Polaris reading, search and
  adoption surfaces. Rejection is recorded on the authoritative work item;
  retained history is not adoptable prose.
- Rejected or unclassifiable provider output is never retained as diagnostic
  prose. Record only permitted error kind, identity/digest and bounded metadata.
- Structured run summaries, work warrants, decisions, materialization mappings,
  known cost/token totals, evidence identities and hashes, and reconciliation
  outcomes survive every compaction in their owning homes. Cleanup does not
  delete this preservation set or convert missing usage into zero.
- Raw transcripts and verbose logs may expire under declared policy. Each
  compaction is an identified, durable record; retention events identify affected
  artifacts so dependent claims can cite the event. Independently governed review
  artifacts keep their preservation obligations and historical bindings.
- A claim whose only substantiation expired renders Unknown citing the retention
  event, never absence or a confident reconstruction from its summary. Preserved
  summaries retain their recorded tiers. Missing artifacts render broken references
  and affect tier in the next identified evaluation; display queries never rewrite
  immutable evaluation conclusions or upgrade tiers.
- Provider expiry does not erase retained confirmation captures. Later authorized
  re-confirmation produces a new observation. A preserved hash without the required
  capture or another satisfied RFC4-13 route caps at report-fact, visibly; it cannot
  establish gate-backed evidence. No records found remains visually and queryably
  distinct from nothing happened.
- Authored composition lives in the intent home, is versioned and individually
  revertible, and survives offboarding. Projection cleanup never deletes it.
- Export needs separate destination/content authorization and preserves draft or
  authored state. Neither retention nor recovery authorizes additional source
  reads, provider calls or remote publication.

## Review protocol

Within the bounded run, an independent preparation stage creates or validates
the source inventory and project-specific reader questions from the admitted
snapshot. It runs in a separate request context that receives sources and
governing questions, not candidate prose, drafting instructions or the authoring
conversation. Producing an inventory and draft in one response does not establish
this independence. Its provider
calls and review consume the same declared run budget. The owner is not required
to hand-author an inventory, expected answers or a project-specific outline before
starting. These artifacts are frozen before candidate narrative drafting. The opening must explain the supported purpose and thesis; the concise
account must explain motives, promises and refusals; deeper reading must explain
capability relationships and reach exact intent. Review each stopping depth before
using deeper material to answer its questions.

The fidelity reviewer receives the owning admitted sources as well as the
inventory and candidate. It checks inventory accuracy/completeness against those
sources before using it for coverage. The fidelity record covers every material
inventory entry and every generated claim-bearing block. It identifies explicit justified omissions, unsupported
claims and misplaced/unused anchors. Labelling unsupported speculation Inferred
cannot make it eligible. The rendered review records desktop/mobile and keyboard
experience, including source/path walls, dead or hidden destinations and reference
material that overwhelms the argument.

Confident source-induced factual errors, inability to explain a supported central
thesis or capability relationships, unresolved material omissions, inaccessible
required paths and blocking visual findings prevent completion. Record failures
and their repairs; a changed artifact requires a fresh applicable evaluation.
Two independently admitted real project domains and real source-change
regeneration are required. At least one case must need synthesis across verbose
or scattered sources, so a polished input document cannot stand in for the engine.

## External completion evidence

The run's internal preparation and reviews are product behavior, not the test
oracle for declaring the generator complete. Independent product evaluators
freeze their questions and expected source-backed answers outside the generator
under test before candidate drafting. They do not derive their denominator or
expected verdict from its inventory, outline or review output. This evaluation
work is distinct from the ordinary owner start flow and does not require owners
to prepare a dossier for every generation request.
