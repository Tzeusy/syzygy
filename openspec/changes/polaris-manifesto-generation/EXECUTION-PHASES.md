# Generator implementation phases — candidate scope

This is proposed phase applicability for the specification and implementation
package. It is not an owner N/A judgment, an act or permission to implement.
The full owner-facing generator, two real projects and changed-source proof remain
mandatory completion criteria. Finishing an earlier phase cannot close the goal.

## Phase A: reusable mechanics

Implement the source/draft contracts, immutable identities and support, bounded
pure stage controller, dependency invalidation, trusted rendering and fixture
adapters. A thin operator seam exercises the complete data path with explicit
synthetic inputs and effects. It does not create or mutate live scheduler items,
call a real provider, serve owner effect controls, or read another project.
Its previews remain identified test/draft artifacts rather than production or
real-project evidence.

Requirements 001-012, 014-019 and 025 provide the data/reading/failure behavior for
these mechanics. Requirements 013, 020-024 and 026-029 remain integration
obligations; their interfaces are preserved and their implementation/evidence
is not claimed by Phase A. No new normalized-worker projection is introduced in
this phase. Every applicable RFC7 consequence still needs approved mapping or
the required owner-bound N/A before the corresponding observable implementation.

## Phase B: real effects and complete owner flow

Integrate the registered source/provider/lifecycle/artifact adapters, separate
protected host, browser/machine admission, durable audit, work materialization,
start/progress/cancel/resume/review/repair and the fixed project reading entry.
Use the same core from Phase A. The CLI remains a diagnostic/operator interface;
manual record assembly cannot replace the owner flow.

Generation-stage panels carry typed stage/receipt facts and an explicit link to
the owning drafting work item. They are not a replacement for its lifecycle.
The following consumers project work state and therefore must retain requirement
028's qualified raw, normalized and chain fields: the drafting-work drawer,
Trajectory work rows, work filters/counts, work exports and machine work answers.
Narrative prose, diagram nodes, glossary and stage receipts do not become work
items merely because work produced them.

The generator does not manufacture or infer a worker-liveness bound from model
timeout, run deadline or receipt cadence. An admitted execution profile with no
effective worker bound uses the existing activity-undetermined predicate; its
actual missing-bound state remains visible. No profile may silently discard or
replace an effective bound to reach that case.

If a selected profile/consumer requires a work-state case for which the accepted
mapping has no predicate, that projection is unsupported and the affected live
run is not admitted until its required mapping/act is effective. A different
profile is an explicit owner choice, not automatic fallback. In particular,
claimed work with an effective bound and no qualifying VCS/PR signal cannot be
reported active, assigned an invented absence value, or treated as fully
conformant merely because provider receipts exist. Any required predicate
amendment is resolved at this integration boundary, not by changing source or
asset validation. This is a refusal boundary, not proof that the unsupported
case has been implemented.

## Phase C: real quality, portability and regeneration

Complete the final real-project proof using the identical engine, prompts,
validators, renderer and supported execution profile. Project source identities,
audience/profile content and separately effective permissions may differ.
Mechanical fixtures, a CLI-only run or unknown mandatory owner-flow behavior
cannot satisfy this phase.

Use independently admitted real revisions to exercise a meaning change. Existing
historical and later revisions may be suitable; the proof must actually revise
the prior bundle from changed source, not merely display two unrelated pages.
Do not edit an observed project just to construct a test without write consent.
Frozen reader questions, independent whole-source fidelity, actual full-page
visual/keyboard review and repair confirmation remain required.

## Approval and phase claims

The owner package must name the phase scope it authorizes. Source/provider/write
permissions are still evaluated at their effect seams. A phase-specific approval
is not approval to bypass later requirements. A whole-generator completion claim
requires all three phases and every applicable requirement to be satisfied.
Unresolved normalized-worker support is reported specifically; it is neither a
reason to call Phase A complete before it works nor a reason to claim the full
owner workflow complete while a required work projection is unsupported.
